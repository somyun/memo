# Windows 11 "바탕화면 보기" 오버라이드 — 기술 정리

## 1. 원래 목표

Windows 11 환경에서 다음 조건을 모두 만족하는 앱을 만드는 것이 목표였다.

1. Windows 11 환경에서 사용
2. 바탕화면(아이콘 포함)보다 항상 위에 배치
3. 일반 앱들과 마찬가지로 최근 활성화 순서(MRU)로 배치
4. Win+D 또는 시계 옆 "바탕화면 보기" 코너 클릭(이하 바탕보기) 시에도 조건 2를 계속 만족
5. 다른 앱들과 함께 MRU 순서로 배치된 상태(맨 위/중간 어디든)에서 바탕보기를 했다가 다시 바탕보기를 누르면, 토글 이전의 MRU 순서로 정확히 복귀
6. 어떤 방법을 쓰든 부드럽고 자연스러운 전환, 깜빡임 없음, 동작의 확실성 보장

## 2. 결론

**가능했다.** 다만 OS의 기존 "바탕화면 보기" 토글 동작에 끼어 들어가려는 접근(예: Owner=Desktop 트릭, SC_MINIMIZE 가로채기)은 전부 구조적으로 불안정했고, **트리거(Win+D, 코너 클릭) 자체를 완전히 가로채서 토글 동작 전체를 직접 구현**하는 방향만이 안정적으로 동작했다.

핵심 설계 원칙은 다음 한 줄로 요약된다:

> **OS가 토글 과정에서 무엇을 하든 신경 쓰지 않고, 토글 시작 시점의 상태를 스냅샷으로 찍어둔 뒤, 종료 시점에 그 스냅샷대로 강제로 복구한다.**

당초에는 "Z-order를 건드리지 않는 API만 쓰면 복구 로직이 필요 없다"는 가정으로 시작했지만, 이 가정이 실제로는 틀렸다는 게 테스트 과정에서 드러났고, 그 대신 "명시적 스냅샷 + 강제 재조립" 방식으로 전환한 것이 실질적인 해결책이었다.

## 3. 트리거 가로채기

### 3.1 Win+D

AHK v2의 `#d::` 핫키 정의만으로 OS 기본 처리보다 우선 적용된다. 별다른 이슈 없음.

### 3.2 코너 클릭 ("바탕화면 보기" 버튼)

**시행착오**: Windows 10까지 유효했던 `Shell_TrayWnd → TrayNotifyWnd → TrayShowDesktopButtonWClass` 자식 윈도우 체인이 현재 Windows 11 빌드에서는 존재하지 않는다. Win11에서 시계/트레이 아이콘/바탕화면 보기 버튼이 전부 `TrayNotifyWnd` 하나의 윈도우 위에 합성(composite) 렌더링되는 비주얼 요소로 통합되었기 때문이다. Window Spy로 확인해도 셋 다 같은 `ClassNN`으로 잡힌다.

**채택한 해법**: 별도 HWND를 찾으려는 시도를 포기하고, **저수준 마우스 훅(`WH_MOUSE_LL`, 코드 14)으로 좌표 기반 차단**을 사용했다.

```ahk
hookCb := CallbackCreate(MouseHookProc, "Fast", 3)
hook := DllCall("SetWindowsHookEx", "int", 14, "ptr", hookCb, "ptr", 0, "uint", 0, "ptr")
```

`Shell_TrayWnd`(및 멀티 모니터의 `Shell_SecondaryTrayWnd`)의 우측 끝 12px 영역에서 `WM_LBUTTONDOWN`(0x201)/`WM_LBUTTONUP`(0x202)이 감지되면 `CallNextHookEx`를 호출하지 않고 `1`을 반환해 메시지를 삼킨다. **이걸로 네이티브 바탕화면 보기 토글이 실제로 발동하지 않는다는 게 직접 테스트로 확인됨.**

검토했으나 폐기한 대안: `TaskbarSd` 레지스트리 값(0으로 설정 시 네이티브 코너 버튼 자체를 비활성화)을 끄고 그 자리에 직접 투명 윈도우를 올리는 방식도 검토했다. 기술적으로는 동작 가능하지만, 앱이 비정상 종료(강제 종료/크래시/정전)됐을 때 `TaskbarSd`를 1로 복구하지 못하면 바탕보기 기능 자체가 영구적으로 망가지는 리스크가 있어 폐기했다. 마우스 훅 방식은 시스템 설정을 전혀 건드리지 않으므로 이 리스크가 원천적으로 없다.

참고로 Windows 11에서는 작업표시줄 우클릭 메뉴에서 "바탕화면 보기" 항목 자체가 빠져 있어(설정으로 가는 메뉴만 존재), 핫키·코너 클릭 외의 제3의 우회 경로는 고려하지 않아도 된다.

## 4. Z-order 보존 — 핵심 버그와 해결 과정

### 4.1 잘못된 초기 가정

> "`SW_MINIMIZE`/`SW_SHOWNOACTIVATE`는 표시 상태(iconic)만 바꾸고 Z-order 슬롯은 그대로 둔다. 그러니 순서를 따로 복구할 필요가 없다."

이 가정은 **틀렸다.** 실제 테스트에서 다음 증상이 나타났다:

- 복귀 후 순서가 토글 이전과 다름
- 복귀할 때마다 항상 같은(원래 순서와 무관한) 고정된 패턴으로만 정렬됨
- 테스트 앱이 원래 중간/하단에 있었어도 복귀 후 항상 맨 위로 올라옴

**원인**: `SW_MINIMIZE`는 창을 최소화시키면서 Z-order상 하단 쪽으로 밀어낸다. 한 번도 최소화되지 않은 창(테스트 앱)은 그대로 있는데 주변 창들이 전부 아래로 밀려나니, 상대적으로 테스트 앱이 맨 위로 올라온 것처럼 보이는 것이다. 그리고 복귀 시점의 순서는 "민 순서"에 의해 결정되는 별개의 패턴이라, 항상 같지만 원래 순서는 아니었다.

### 4.2 해결 — 스냅샷 + 강제 재조립

1. 토글 시작 시점에 `EnumWindows`로 전체 Z-order를 스냅샷으로 캡처 (테스트 앱 포함)
2. 최소화 대상 창들만 `SW_MINIMIZE`
3. 복귀 시: 일단 전부 `SW_SHOWNOACTIVATE`로 보이게 만듦 (이 단계의 순서는 엉켜도 무관)
4. **`BeginDeferWindowPos` / `DeferWindowPos` / `EndDeferWindowPos`**로 스냅샷 순서를 한 번에 강제 재조립

```ahk
hdwp := DllCall("BeginDeferWindowPos", "int", n, "ptr")
loop (n - 1) {
    hdwp := DllCall("DeferWindowPos", "ptr", hdwp,
        "ptr", snapshot[i+1], "ptr", snapshot[i],
        "int", 0,"int", 0,"int", 0,"int", 0,
        "uint", SWP_NOSIZE | SWP_NOMOVE | SWP_NOACTIVATE, "ptr")
}
DllCall("EndDeferWindowPos", "ptr", hdwp)
```

`DeferWindowPos`는 여러 창의 위치/순서 변경을 모아서 화면 갱신 한 번으로 일괄 적용하는 API라, `SetWindowPos`를 하나씩 순차 호출했을 때 생길 수 있는 중간 단계의 시각적 뒤섞임(깜빡임)도 같이 제거된다.

**교훈**: minimize/restore 과정에서 Z-order가 내부적으로 어떻게 흐트러지는지 예측/방지하려 하지 않고, 결과만 강제로 맞추는 쪽이 훨씬 견고했다.

## 5. 포커스(활성창) 사이드이펙트

**증상**: 복귀 후 테스트 앱이 Z-order상 맨 위가 아니어도 항상 활성(active) 상태가 됨.

**원인**: 여러 창을 한꺼번에 `SW_MINIMIZE`할 때, 그중 현재 포커스를 가진 창이 최소화되는 순간 OS가 자동으로 "다음 창"을 활성화시킨다. 이 과정이 반복되면 결국 한 번도 최소화되지 않은 테스트 앱이 활성 상태를 떠안게 되고, 복귀에 쓰는 `SW_SHOWNOACTIVATE`는 의도적으로 포커스를 주지 않는 호출이라 아무도 그 포커스를 되찾지 않는다.

**해결**: 토글을 켜기 직전에 `GetForegroundWindow()`로 활성창을 기억해두고, 복귀 마지막 단계에서 `WinActivate`로 명시적으로 되돌린다.

## 6. 외부 개입으로 인한 상태 불일치 (stale state)

**증상**: 바탕보기 토글로 복귀하지 않고 작업표시줄을 직접 클릭해 특정 창을 연 뒤, 다시 바탕보기를 누르면 현재 상태를 기준으로 최소화하는 게 아니라 이전에 저장해둔 낡은 스냅샷을 그대로 복원해버림.

**원인**: 내부 상태(`g_isDesktopShown`)는 단순 boolean이라, 우리가 가로채는 경로(Win+D, 코너 클릭)를 거치지 않고 사용자가 작업표시줄 등으로 직접 창을 복원하면 실제 상태와 내부 상태가 어긋난다(stale).

**해결**: 매 토글 시도마다 "우리가 최소화시킨 창들이 지금도 전부 정말 최소화 상태인지"를 검증(`AllTouchedStillMinimized`)하고, 하나라도 깨져 있으면 내부 상태를 리셋한 뒤 현재 화면 상태를 기준으로 새로 시작한다.

## 7. 최종 구성요소 정리

| 구성요소 | 역할 |
|---|---|
| `#d::` 핫키 | Win+D 가로채기 |
| `MouseHookProc` (`WH_MOUSE_LL`) | 코너 클릭 좌표 감지 및 차단 |
| `GetTrackedWindows` / `IsTrackedWindow` | Alt-Tab류 필터로 "진짜 앱 창" 목록 추출 (테스트 앱 포함) |
| `MinimizeWindows` | 토글 ON: 활성창·전체 순서 스냅샷 → 대상 창 최소화 |
| `RestoreWindows` | 토글 OFF: 전체 복원 → DeferWindowPos로 순서 강제 재조립 → 포커스 복구 |
| `AllTouchedStillMinimized` | 매 토글 시 상태 유효성(stale 여부) 검증 |
| 트레이 메뉴 | 수동 토글 테스트, 강제 전체 복원(안전장치) |

## 9. 남아있는 미검증/한계 (참고용)

- **`CORNER_BTN_WIDTH`(현재 12px)**: 해상도/DPI/스케일링에 따라 미세 조정이 필요할 수 있음. 환경별 실측 권장.
- **멀티 모니터**: `Shell_SecondaryTrayWnd`도 같이 체크하도록 해뒀지만, 실제 멀티 모니터 환경에서의 직접 테스트는 아직 안 됨.
- **바탕보기 중 추가 상호작용**: "바탕보기 상태" 동안 사용자가 새 창을 열거나 테스트 앱과 상호작용하는 등의 복합 시나리오는 별도로 더 테스트해볼 필요가 있음.
- **호버 피크**: Windows 11에서는 코너 버튼 호버 시 미리보기(peek) 효과가 제거되고 Win+,(쉼표)로 대체되었으므로, 이 구현에서는 별도로 다루지 않음 (요구조건에도 명시되지 않았음).

## 10. 결과물
